# 다이제스트 LLM 연결 진단 (2026-09-10 갱신)

## 목적과 변경 범위

반복된 `terminated; cause=ECONNRESET: read ECONNRESET`을 조사하기 위해 9/8에 계측, 9/9에 최종 Pro SSE 수신을 추가했다. **9/10부터 정식 `deepseek-flash`(V4.1 Flash) 및 호환 DeepSeek 모델에서 명시적으로 Thinking을 켠 최종 요청에도 SSE를 적용한다.** 오류 코드 하나나 스트리밍 적용만으로 원인을 확정하지 않는다.

- 기본은 최종 Thinking ON 1회 → 실패하면 자료 정리 모델의 설정(기본 OFF)으로 최대 1회 대체다. 공식 DeepSeek 엔드포인트는 모델 이름과 무관하게 단계 정책을 적용하며, Settings의 명시적 ON/OFF 선택이 환경변수 기본값보다 우선한다. 동일 모델도 ON→OFF 전환이면 가능하며 대체 결과의 피드 정리는 보류한다. 새 `DIGEST_FINAL_THINKING`/`_TOKENS`가 기존 `DIGEST_PRO_THINKING`/`_TOKENS`보다 우선한다. ON 최대 토큰 설정은 최소 49,152를 확보하며 고정 사용량을 뜻하지 않는다. 앱 타임아웃·운영 스케줄 변경·자동 분석 직렬화는 추가하지 않았다.
- 최종 모델의 추론/본문 델타를 수신하며, `finish_reason=stop`, `[DONE]`, 비어 있지 않은 본문을 확인한 경우만 완성본으로 반환한다. 중단·잘림·마커 누락 때는 부분 본문을 버리고 기존 폴백으로 보낸다.
- Thinking OFF 호출의 기본 수신은 비스트리밍이다. 사용자가 선별·정리를 ON으로 바꾸면 해당 단계에도 SSE를 적용한다. 사용자가 `LLM_EXTRA_BODY.stream=true`를 명시했다면 다른 호출도 그 설정을 존중해 SSE로 처리한다. 사용자는 기존처럼 생성이 끝난 보고서를 목록에서 연다.
- 전송 청크는 SSE 이벤트나 생성 토큰과 같지 않다. 연결 유지용 바이트와 실제 추론/본문 델타를 별도로 구분한다. 계측 자체는 추가 LLM 요청을 보내지 않는다.
- DB 마이그레이션 없음: 실패 계측은 기존 `digests.meta.models.stages.*.errors[].diagnostics`에 저장한다. 성공 수치는 서버 로그로 비교한다.

## 2026-09-09 14시 실패 실측

확인 기준 배포는 `cc02628`. 최종 Pro 요청은 **2026-09-09 14:00:33 KST**에 시작했다. 실패 뒤 Flash 폴백이 리포트를 완성했으므로, 자동 작업 전체가 저장에 실패한 경우와 구분한다.

| 항목 | 관측값 |
|---|---|
| 전송 방식 / 실패 단계 | 비스트리밍 / `reading_body` |
| HTTP 상태 / 헤더 도착 | 200 / 407ms |
| 첫 바이트 | 60,407ms |
| 전체 소요 시간 | 240,436ms |
| 마지막 바이트 | 240,434ms |
| 마지막 바이트 이후 실패까지 | `idleMs=2` |
| 총 수신량 | 4바이트 / 전송 청크 4개 |
| 제공자 사용량 / 종료 사유 | 수신하지 못함 |
| 종료 오류 | `ECONNRESET` |

[DeepSeek 공식 문서](https://api-docs.deepseek.com/quick_start/rate_limit)는 요청 대기 중 비스트리밍에는 빈 줄, 스트리밍에는 SSE 연결 유지 주석을 보낼 수 있다고 설명한다. 이번 수치는 완성 JSON이 오기 전 연결 유지용 빈 줄만 받은 패턴과 부합한다. 원문 바이트를 기록하지 않았으므로 빈 줄이었다고 확정할 수는 없다.

HTTP 200은 헤더 도착만 입증한다. 이 기록에는 `finishReason`이나 토큰 사용량이 없어 토큰 한도 초과로 해석할 근거가 없다. `idleMs=2`이고 앱 자체 타이머도 없으므로 앱의 유휴 시간 제한이 종료시켰다는 증거도 없다. DeepSeek 서버와 중간 프록시·네트워크 중 어느 구성요소가 연결을 끊었는지는 운영 로그 없이는 구분할 수 없다. 스트리밍은 결과가 생성되는 동안 델타를 받을 수 있게 하지만, 제공자 대기나 네트워크 단절이 없어지는 것을 보장하지 않는다.

사용자가 비교한 자동/수동 실행은 동일한 모델 설정·Thinking·예산을 사용한다. 다만 자동 낮분은 **9/9 07:00~14:00**, 수동 `2026-09-10`은 **9/9 07:00~9/10 07:00** 창이다. `analyses.createdAt`으로 글을 고르므로 수동본은 14시 이후 분석 완료된 글도 포함할 수 있다. 입력이 같은 재현 시험으로 간주하지 않는다. 13시 적체 분석과 14시 다이제스트가 겹칠 가능성은 코드에 있지만, 이 기록만으로 연결 종료의 원인이라 볼 수 없다.

## 배포 후 확인 방법

로컬 검증은 `npm test` 129/129, `npm run typecheck`, `npm run build`, `git diff --check` 모두 통과했다. 스트림 종료 처리에 대한 별도 코드 검토도 완료했다. 아래 실서버 확인은 별도로 남아 있다.

1. 해당 다이제스트 → **실패 원인 N건 보기** → **진단 정보 복사**를 누른다. 복사 차단 시 상세 JSON을 직접 복사한다.
2. 복사한 JSON과 발생 시각을 함께 확인한다. 공유 범위를 넓힐 때는 실제 실행/요청 ID를 제거하고 수치만 남긴다.
3. Railway 로그에서 JSON의 `runId`를 검색한다. `llm_start`, `llm_success`, `llm_failure`의 모델·단계·시도를 비교한다. 성공 호출도 수치만 로그에 남는다.
4. 최종 `deepseek-flash` 호출의 Thinking ON·`stream:true`, 첫 추론/본문 델타 시각, 종료 사유, `streamCompleted`를 확인한다. 연결 유지 바이트만 도착한 실행과 모델 출력이 진행되다가 끊긴 실행을 구분한다.
5. 다음 자동 실행에서 최종 Thinking ON 정상 완성과 OFF 대체 여부를 확인한다. 모델명이 같아도 `phase=fallback`과 `fallbacks`를 확인한다. 코드 배포와 실제 자동 생성 성공 여부는 별도로 검증한다. 기존 실패본에는 새 스트리밍 계측을 소급할 수 없다.
6. 시작 로그만 있고 종료 로그가 없다면 같은 시각의 재시작·배포·컨테이너 종료 로그를 확인한다. 폴백까지 실패해 보고서가 저장되지 않아도 Railway 실패 로그는 남는다.

## 필드 해석

- `awaiting_headers`: HTTP 헤더 전 실패. DNS/TLS/연결/제공자 지연 등은 코드와 운영 로그로 추가 구분한다.
- `reading_body`: 헤더 이후 본문 수신 중 실패. 비스트리밍 JSON과 스트리밍 SSE 모두 완성 전 끊길 수 있다.
- `parsing_response`: JSON 또는 SSE 이벤트 해석 실패. 제공자 오류 본문이나 파싱 오류 원문은 진단에 기록하지 않는다.
- `validating_response`: 수신 결과의 종료 상태·토큰 한도·빈 본문 등을 판정하다 실패. `finishReason`, 제공자 보고 토큰 수, `streamCompleted`를 함께 본다.
- `durationMs`, `headersMs`, `firstByteMs`, `lastByteMs`는 요청 시작 기준 시간이다. `idleMs`는 본문 수신 실패 시 마지막 데이터(없으면 헤더) 이후 경과 시간이다. 연결 유지 데이터도 바이트 시각에는 포함되므로 `firstByteMs`를 첫 생성 토큰 시각으로 보지 않는다.
- `stream`: 해당 요청이 SSE를 사용하는지 나타낸다. 과거 계측에 필드가 없으면 수신 방식을 새 필드만으로 추정하지 않는다.
- `firstReasoningMs`, `firstContentMs`: 최초의 비어 있지 않은 추론/본문 델타를 받은 시각이다(요청 시작 기준). SSE 주석·역할 이벤트·사용량 이벤트는 이 값을 채우지 않는다. 값이 없으면 해당 델타를 관측하지 못했거나 이전 계측 버전인 것이다.
- `streamCompleted`: SSE의 `[DONE]` 수신 여부다. `true`만으로 보고서 성공을 뜻하지 않는다. 정상 종료(`stop`)와 유효 본문도 필요하다. 중간까지 받은 텍스트는 스트림 실패 때 성공본으로 저장하지 않는다. SSE 종료 규약은 [DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/) 참조.
- `systemChars`, `userChars`는 입력 글자 수, `requestBytes`는 직렬화 요청 크기다. 글 수 그 자체가 아니며 입력 크기와 실패 시간의 상관관계를 비교하는 용도다.
- 토큰 사용량 응답을 못 받은 경우 **확인 불가**이지 0토큰/무료가 아니다. 스트림이 끊기면 마지막 사용량도 못 받을 수 있다. `reasoningChars`는 문자 수이며 토큰과 합산하지 않는다.
- `appTimeoutMs:null`: 앱 자체 AbortSignal 타이머를 설정하지 않았다는 뜻일 뿐 Node/프록시/제공자 제한이 없다는 뜻이 아니다.

## 개인정보와 한계

진단에는 프롬프트·기사 본문·사고 텍스트·API 키·전체 URL·전체 응답 헤더를 저장하지 않는다. 호스트명과 허용 형식의 요청 ID/오류 코드만 남긴다. 스트림에서도 추론 텍스트는 축적하지 않고 문자 수만 센다. 이 문서에는 실제 실행/요청 ID나 기사 데이터를 포함하지 않는다.

기존 다이제스트에 소급해서 계측을 채울 수 없다. 새 필드는 새 버전 배포 후 실행부터 적용된다. Anthropic SDK 경로는 단계별 HTTP 계측 없이 시도별 총시간만 기록한다. 특정 서버의 장애나 입력 증가와 실패의 인과관계는 수치 하나로 확정하지 않는다.

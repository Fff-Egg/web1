# LLM 사용량과 본문 처리 비용

2026-09-21 추가, 2026-09-22 출력 제한의 원인 수정·실패 진단·재시도 보호 확장. Settings 상단에서 실제 서버 실행 시각과 최근 한국시간 7일의 기록을 조회한다. 기본 선택은 **오늘(한국시간, 진행 중)**이며 이전 날짜와 최근 7일 전체도 선택할 수 있다. 조회·새로고침은 유료 API를 호출하지 않는다.

## 비용을 줄이는 처리

- RSS 제공 본문과 추출 원문은 공백 차이만 정규화해 포함 여부를 비교한다. 동일 본문을 두 번 붙이지 않되 서로 다른 내용·제목·숫자는 보존한다.
- X·텔레그램 연결 기사에서 알려진 추적 매개변수만 다른 URL과 동일 추출 본문은 한 번 읽고 모든 출처 참조를 남긴다. 기능 매개변수는 유지하며 원문 수집의 내부 주소 차단은 그대로다.
- 수집기와 분석기는 글별 같은 프로세스 잠금을 사용한다. 본문/수집 범위가 같으면 reading_cache 필드를 덮어쓰지 않는다. 내용이 바뀌면 요약 캐시를 무효화한다. DB 쓰기도 본문·제공 본문·수집 시각을 비교해 오래된 스냅샷의 쓰기를 거부한다.
- 이는 별도 서버 인스턴스 간 LLM 호출을 합치는 분산 잠금은 아니다. 기존 저장 글을 일괄 갱신하거나 유료 재분석하지 않는다. 새 수집 및 명시적 원문 갱신에 적용된다.

## 2026-09-22 확인한 반복 실패와 복구

9/21의 중복 본문 제거·요약 캐시 보호만으로 해결되지 않은 비용 증가를 단계별 사용량과 운영 로그로 다시 확인했다. 전체 읽기에서 `finish_reason=length`와 출력 3,200토큰, 선별에서 출력 1,400토큰인 실패가 반복됐다. 실패한 전체 읽기는 완료 구간을 저장하기 전에 예외가 발생하고, 분석 완료 행도 없어 다음 주기에 같은 조건으로 다시 요청할 수 있었다. 실패한 응답도 이미 생성한 출력 토큰은 소비한다. 이는 입력 캐시 할인이나 본문 중복 여부와 별개인 재시도 문제다.

**9/13 변경과의 연결**: 커밋 `3819e5c`는 선별 입력의 앞 4,000자 제한을 없애고, 긴 글의 선별 전에 전체 읽기를 추가했다. 새 전체 읽기는 12,000자마다 약 2,000자 사실 요약을 요구하면서 사용자에게 보여줄 요약 지침까지 함께 넣었고 출력 상한은 3,200토큰이었다. 여러 사건의 직접 영향·연결 가설·검증 데이터까지 요구하는 저장 지침이 중간 압축 단계에도 적용될 수 있었다. 선별은 입력이 늘었지만 기존 600/1,400토큰 상한을 유지했다. 이 코드 변경은 9/14부터 늘어난 출력의 유력한 촉발 조건이며, 같은 출력 제한 실패와 재호출 경로는 9/22 로그로 확인했다. 다만 단계별 기록 시작 이전인 9/14의 실패 횟수·구간·비용 기여도를 소급 확정할 수는 없다.

### 9/22 저녁 재확인

사용자가 추가한 CSV의 9/22 비용은 정오 **$0.794674974**에서 저녁 **$1.409376390**으로 늘었다. 증가분 **$0.614701416**은 모두 한국시간 **13~15시** 행에 있고 Flash 비혼잡 단가가 적용됐다. 이번 CSV 비교에서 10~13시와 15시 이후 추가분은 없었다. 보고서 07/14시와 자동 선별의 10~13시·15~19시 대기 정책은 변경하지 않았다.

정오 이후 전체 읽기 요청은 **293회 증가: 정상 응답 248회, 출력 제한 실패 45회**였다. 저녁 당일 누계는 전체 읽기 614회 중 실패 313회이며, 화면의 비혼잡 단가 추정 비용은 전체 읽기 약 **$1.0957**, 전 단계 합계 약 **$1.4057**였다. 이 추정과 CSV 실제 비용은 서로 다른 집계이므로 혼용하지 않는다. 증가분에는 밀린 글의 정상 처리도 포함된다. 누적 실패 수가 늘었다는 사실만으로 같은 구간을 계속 재시도 중이라고 해석하지 않는다.

18:49 운영 상태 조회에서는 보류 14건(전체 읽기 6건, 요청 거절 8건), 시간 대기 0건, 분석 가능 74건을 확인했다. 새 HTTP 400 8건은 제공자의 `content_policy` 분류였고, 이전 상세 미수신 248건은 여전히 원인 미상이다. 콘텐츠 정책 거절을 출력 한도 문제와 섞거나 같은 조건으로 반복 실행하지 않는다. 개별 글의 실제 읽기 보류 원인은 아래 처리 내역에서 확인한 뒤 대상으로 삼는다.

코드 점검에서는 한 글의 6,000자 구간이 실패하고 3,000자 하위 구간은 성공해도, 뒤의 구간마다 다시 6,000자를 시도하는 비용 경로가 남아 있었다. 가상 응답으로 72,000자 글에서 실패 12회·성공 24회, 78,000자 글에서 실패 13회·성공 24회 후 보정 한도 보류를 재현했다. 아래의 글별 입력 상한 학습은 이 경로를 줄이는 수정이며, 실제 보류 글의 성공·품질 검증 완료를 뜻하지 않는다.

### 전체 읽기

- 내부 읽기는 **원문에 있는 사건·주체·수치·날짜·조건·반론·결론을 압축하는 사실 메모**만 만든다. 사용자 Feed 요약의 문장 형식과 새로운 직접/2차/3차 영향 해석은 이 단계에 주입하지 않는다. 원문 작성자가 제시한 영향·가설은 보존하며 사용자 요약 지침은 후속 선별에서 계속 적용한다.
- 12,000자 이하 글은 추가 요약 호출 없이 그대로 넘긴다. 그보다 긴 글의 미완료 기본 구간은 **첫 API 호출 전에 최대 6,000자씩 무손실 이등분**한다. 모든 문자를 입력에 포함하고 이모지 쌍을 보존한다. 구간별 짧은 사실 항목을 목표로 하여 완성 보고서 형식으로 확장하지 않으며, Thinking OFF의 출력 상한 3,200토큰은 여유 한도로 유지한다.
- 기존 12,000자 기본 구간과 캐시 키는 호환용으로 유지한다. 완료된 전체 요약·기본 구간·하위 구간을 재사용하고, 아직 성공하지 못한 구간만 새 지침으로 처리한다. 키 계산의 구 지침 문자열과 실제 API의 새 내부 사실 지침은 의도적으로 구분한다.
- 제공자가 여전히 출력 제한 실패를 반환한 구간은 추가로 이등분한다. 잘린 출력 자체는 요약으로 저장하지 않는다.
- 실패한 상위 구간의 분할 계획을 **하위 요청 전에** 저장한다. 하위 구간의 성공 결과도 개별 저장하므로 다음 실행은 실패한 상위 구간이나 완료한 형제 구간부터 다시 읽지 않는다.
- **글별 입력 상한 학습**: 출력이 잘리면 실패한 구간을 무손실 이등분한 크기로 `readingCache.recovery.inputCharLimit`를 낮춰 하위 요청 전에 저장한다. 같은 글의 이후 미완료 구간은 이 상한에 맞춰 먼저 나누므로, 앞에서 실패한 큰 입력 크기를 뒤의 구간마다 다시 유료 시험하지 않는다. 앞 구간이 성공했어도 뒤의 조밀한 구간이 실패하면 상한을 낮추며 자동으로 다시 높이지 않는다. 기존 실패 분할 계획도 완료된 부모 안의 하위 계획까지 살펴 상한을 추론한다. 이미 완료한 구간은 크기와 무관하게 재사용한다.
- 복구 분할은 최대 3단계이며, 3,000자 미만 구간의 실패는 그 실행에서 추가 보정하지 않고 보류한다. 출력 제한에 따른 추가 하위 요청은 글의 동일 읽기 캐시당 최대 24회이며 요청 전에 횟수를 저장한다. 정상 첫 요청과 학습된 상한에 따른 이후 사전 분할 요청은 이 보정 호출 수에 포함하지 않는다. 사전 분할 계획은 `proactiveSplits`로 구분한다. 명시적으로 보류를 해제해도 학습된 상한·완료 구간·분할 계획은 유지하므로 더 작은 사전 분할로 이어갈 수 있다.
- 복구 정책 v2로 처음 진입한 **미완료 캐시만** 이전 보류·보정 횟수를 한 번 초기화한다. 성공 구간과 이미 실패한 상위 구간의 분할 계획은 보존하고 정책 변경을 요청 전에 저장한다. 같은 v2 정책에서 다시 보류되면 이후 자동 실행이 반복해서 풀지 않는다. 완료 캐시는 정책 변경으로 재생성하지 않는다.
- 이번 입력 상한 학습은 기존 `policy:2`와 분석 설정 지문을 유지한다. 이미 보류된 글을 일괄 해제하거나 재분석하지 않는다. 운영 검증은 처리 내역을 확인한 글에 대한 명시적 단건 실행으로 수행한다.
- 복구 한도에 도달하거나 요약이 줄어들지 않으면 `readingCache.recovery.held`에 보류 상태를 저장한다. 이후 같은 읽기 키로 자동 호출하지 않으며, 명시적 재시도 또는 읽기 키에 영향을 주는 본문·모델·요약 지침 변경이 필요하다. 보류된 부분 결과를 완성 보고서로 승격하지 않는다.

### 글 선별과 자동 분석 재시도

`0016_analysis_retries.sql`은 글별 본문·분석 설정 지문, 실패 횟수, 다음 재시도 시각, 보류 여부, 선별 출력 제한 보정 여부를 저장한다. 같은 프로세스의 자동·수동 분석 호출은 실행 중인 배치를 공유한다.

- 선별은 처음부터 중복 설명을 줄이고 필수 JSON을 완성하도록 안내한다. Thinking OFF 기본 출력 한도는 논지 목록이 없으면 **1,600**, 있으면 **2,800토큰**이다(`FILTER_MAX_TOKENS` 명시값 우선). 최대 한도는 고정 소비량이 아니다. DeepSeek 호환 호출은 `response_format: {type: "json_object"}`도 지정하되, 출력 제한·빈 응답 검증은 유지한다. 사용자 관련성·중요도·요약 기준과 전체 입력은 바꾸지 않는다.
- 선별 응답이 출력 제한에 걸리면 간결한 JSON 지침과 보정 예산으로 한 번 복구한다(기본 한도의 경우 3,200/5,600토큰). 보정 전략을 요청 전에 저장해 다음 실행에서 이미 실패한 원래 전략을 반복하지 않는다. 분석 정책 지문 v2는 구 정책에서 보류된 글에 수정된 전략의 새 시도를 허용한다.
- 보정 후에도 출력이 잘리거나 전체 읽기가 복구 한도에 도달하면 해당 글을 보류한다. 요청 자체가 거절된 HTTP 400·404·422도 설정 확인이 필요한 보류로 취급한다.
- 일시적인 연결·처리 오류는 첫 실패 후 30분, 두 번째 실패 후 2시간 기다리며 세 번째 실패 시 보류한다. 관련 본문·설정 지문이 바뀌면 이전 글별 재시도 제한과 구분한다.
- HTTP 401·402·403은 전체 글 분석을 1시간, 429는 30분 대기시킨다. 이미 시작한 동시 요청 외에 남은 배치의 추가 호출을 중단하며, 글별 실패 제한도 적용한다. 재시도 상태 저장에 실패해도 남은 배치를 중단해 기록 없는 유료 반복을 피한다.
- 보류된 글의 본문과 완료된 구간 요약은 보존한다. 분석이 완료되기 전에는 다이제스트 대상이 되지 않는다. 원문 전체 읽기와 선별·자료 정리 Thinking OFF / 최종 Thinking ON 정책은 유지한다.

Settings의 **자동 분석 재시도 관리**는 미분석·분석 가능·재시도 시간 대기·보류 건수와 최근 20개 대기/보류 글, 실패 원인, 재시도 시각을 표시한다. 운영자가 개별 또는 전체 제한 해제를 확인하면 완료된 구간과 분할 계획을 남기고 보류·추가 호출 횟수·글별 실패 제한을 초기화하며 전체 분석 대기도 해제한다. **해제 동작 자체는 LLM을 호출하지 않는다.** 다음 분석에서 이어가고 기존 절약 시간 정책도 적용된다.

Settings의 **최근 7일 반복 실패 글 → 1건 다시 분석**은 확인 후 지정한 미분석 글 하나의 제한만 풀고 즉시 분석한다(`settings.runArticleAnalysis`, 기존 Basic Auth 보호). 일반 제한 해제와 달리 유료 호출이 발생할 수 있으므로 명시적 확인과 결과를 표시한다. 같은 프로세스의 실행 잠금을 먼저 확보해 연속 클릭으로 중복 호출하지 않으며 다른 대기 글 전체를 처리하지 않는다. 전체 분석 대기는 유지하고 선택한 한 글만 그 대기를 우회한다. 이미 완료/삭제된 글은 추가 분석하지 않는다. 가상 UI에서 취소 시 미호출·확인 시 단건 요청을 검증했으며 실제 운영 성공 결과는 별도로 확인한 뒤 기록한다.

**자동 분석 재시도 관리 → 처리 내역**은 저장 본문 전체, 제공 본문/저장 본문의 크기, 수집 범위, 완료 캐시 수, 복구 횟수·보류 원인·학습 입력 상한과 최근 호출 최대 30건을 읽기 전용으로 조회한다(`settings.getArticleAnalysisDiagnostics`, 기존 Basic Auth 보호). 완료 요약 표본은 캐시 키 정렬에서 처음·중간·끝을 고르며 원문 순서를 뜻하지 않는다. 캐시 수/글자 합계는 부모·자식 요약을 함께 포함하므로 고유 원문 처리량으로 합산하지 않는다. 이 조회와 새로고침은 AI 호출·원문 재수집·보류 해제를 하지 않는다.

입력 상한 학습의 가상 호출 검증에서는 72,000자 글이 실패 12회에서 1회로, 78,000자 글이 실패 13회 후 보류에서 실패 1회 후 완료로 바뀌었다. 모든 입력 문자와 이모지, 완료 캐시·키 재사용, 중단 후 상한 복구, 기존 보류 유지도 검사했다. 현재 전체 255개 테스트·타입 검사·프로덕션 빌드가 통과했다. 실제 보류 글의 운영 단건 검증은 별도 완료 기록 전까지 대기 상태다.

## 기록과 해석

`0015_llm_usage.sql`은 요청별 메타데이터를 저장한다. Railway 시작 시 기존 db:migrate 경로로 적용한다. 모델, Thinking, 단계, 글/다이제스트 실행 ID, 시간, 성공 여부, 제공자가 반환한 토큰만 기록한다. 본문·프롬프트·응답 텍스트·키·오류 원문은 저장하지 않는다.

`0017_llm_provider_error.sql`은 제공자 오류의 고정 분류와 허용 목록에 있는 파라미터 이름만 추가한다. 문맥 한도, 출력 토큰 설정, 모델, 미지원 파라미터, 스트림 옵션, JSON 요구/형식, 유니코드, 콘텐츠 정책, 인증, 잔액, 속도 제한, 미상으로 구분한다. 제공자 메시지·오류 코드·본문은 메모리에서만 판별하고 저장/로그/클라이언트 오류로 전달하지 않는다. 과거 HTTP 400의 상세 원인은 기록이 없으므로 새 분류로 소급 추정하지 않는다.

단계: 선별, 전체 읽기, 다이제스트 자료 정리, 최종 작성, 대체 작성, 학습 메모, 개별 심층, 리포트 요약. DeepSeek는 HTTP 호출별 기록한다. Anthropic은 SDK 호출 단위여서 SDK 내부 재시도까지 개별 분리하지 않는다.

사용량은 JSON 및 SSE에서 읽는다. 실패해도 확보한 토큰은 보존하고, 미수신 값은 null로 남긴다. 성공은 LLM 전송/응답 검증 기준으로 이후 업무 저장 성공과 다를 수 있다. 원문 요약 캐시를 재사용해 API를 호출하지 않았다면 요청이 기록되지 않는다. 관측 실패는 모델 호출 재시도나 결과 변경을 일으키지 않는다. 기록을 최대 750ms 기다리고 장애 시 메타데이터를 서버 로그의 `[llm-usage] persist_unavailable`로 남긴다. 늦게 저장된 기록과 로그는 requestId로 중복 제거할 수 있다. 화면은 DB에 저장된 기록만 집계하므로 로그로만 남은 요청은 빠질 수 있다.

선택 기간의 **실패 원인** 표는 단계·모델·Thinking·HTTP 상태·종료 사유별 실패 횟수와 확보한 출력 토큰·참고 비용을 보여준다. 이는 위 전체 사용량의 **부분집합**이므로 다시 더하지 않는다. 수정 전 발생한 요청도 선택 날짜의 합계에 남는다. **최근 7일 반복 실패 글**은 날짜 선택과 별개인 7일 전체의 상위 20항목이다. 같은 글의 여러 구간 실패도 합산하므로 이 횟수만으로 동일 구간의 재호출이라고 단정하지 않는다. 현재 보류 상태는 사용량 이력이 아닌 재시도 관리 패널에서 확인한다.

입력 캐시 적중·미적중·출력을 모두 받은 공식 DeepSeek Flash 요청만 100만 토큰당 $0.003 / $0.15 / $0.60으로 계산한다. 별도 추론 토큰은 출력의 일부이므로 이중 합산하지 않는다. 이는 2026-09-21 공식 요금표의 **비혼잡 단가 기준 참고값**이며 실제 청구액이 아니다. 피크 단가·미수신 토큰·다른 모델·이후 가격 변경은 추정에 반영하지 않는다. 화면은 계산 가능 요청 수를 함께 표시한다. 실제 청구는 제공자의 cost/amount 내역으로 확인한다. 기록 시작 이전의 단계별 비용은 이 기능으로 복원할 수 없다.

## 일정 검증

시도 횟수는 유료 작업 전에 저장하여 서버 중단 뒤에도 유지한다. 중단된 작업은 최소 30분 대기 후 남은 횟수 안에서 이어가며, 세 번째 예약 이후 중단되면 보류한다. 진행 중인 예약도 관리 화면의 시도/대기 건수에 잠시 포함될 수 있다. Feed에서 명시적으로 원문을 갱신하면 이미 분석된 글의 전체 읽기 보류도 해제하며, 완료된 구간과 분할 계획은 재사용한다.

모델 전환(9/10), 전체 본문 수집(9/13), 작업 버튼 수정(9/19) 및 이번 변경에서 크론 시간/절약 대기 정책을 변경하지 않았다. `DIGEST_HOUR`·`DIGEST_MIDDAY_HOUR`가 우선하며 미설정 기본값은 기존 07/17시다. 운영 기록상 07/14시는 서버 환경변수로 설정되어 있다. Settings의 현재 서버 적용 시간은 실제 실행 함수가 해석한 값을 조회한다.

`ANALYSIS_AVOID_PEAK` 기본 활성, `0`이면 해제. 자동 글 분석은 매일 KST 10~13시·15~19시에 대기하고 13/19시에 재개한다. 수집과 명시적 수동 실행에는 이 대기를 강제하지 않는다. 공식 요금표의 혼잡 시간은 중국 휴일 제외 월~금의 해당 시간이고 주말은 비혼잡이다. 앱의 기존 대기는 주말에도 적용하므로 공식 과금 시간보다 보수적이다. 이번 작업에서 그 정책을 바꾸지 않았다.

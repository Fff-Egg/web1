# 전체 본문 수집과 읽기

2026-09-13부터 피드의 앞부분만 분석하던 제한을 제거했다. 수집 가능한 텍스트를 보존하고, 긴 글은 모든 구간을 읽어 종합 분석에 사용할 요약을 저장한다.

## 사용자 동작

- 새 글은 수집·자동 분석 때 적용된다. 기존 피드 글도 다음 다이제스트 입력으로 사용될 때 준비한다.
- Feed/보관함 카드에서 **원문 내용 보기**를 펼치면 저장 본문과 수집 상태를 확인할 수 있다. 이 조회 자체는 LLM을 호출하지 않는다.
- Settings의 **자동 분석 재시도 관리 → 처리 내역**은 보류 글의 저장 본문·완료 요약 표본·분할/복구 상태·학습된 입력 상한·최근 API 호출 최대 30건을 조회한다. 기존 인증이 필요하며 AI 호출, 재수집, 보류 해제를 하지 않는다. 부모·자식 요약을 함께 저장하므로 캐시 개수나 글자 합계는 고유 원문 처리량이 아니다.
- **원문·전체 요약 갱신**은 원문을 재수집하고 종합 입력을 준비한다. 본문·설정이 같으면 저장된 요약을 재사용한다. 별점·분류·기존 분석 시각은 바꾸지 않는다.
- 이미 저장된 보고서는 자동으로 다시 생성하지 않는다. 새 내용을 반영하려면 해당 기간의 새 다이제스트를 생성한다.

## 수집 범위

RSS 및 일반 글은 원문 URL의 HTML에서 본문을 추출한다. 네이버 블로그의 본문 iframe과 소스별 본문 선택자를 지원하며 나머지는 Readability를 사용한다. 제공 본문과 원문 추출 결과가 서로 다른 경우 제공 본문을 함께 보존한다.

X·텔레그램은 게시글을 보존한 뒤 직접 연결된 페이지의 텍스트를 별도 구분해 추가한다. **2026-09-22부터 원 게시글의 참고 링크가 3개를 초과하면 연결 페이지를 하나도 요청하지 않고 원 게시글만 분석한다.** 3개 이하는 기존 방식으로 수집한다. 처음 3개만 선택하는 규칙도, 연결된 기사 안의 링크 수를 세는 규칙도 아니다. 링크 안의 또 다른 참고 문헌까지 재귀 수집하지 않는다. 원문 자체가 2차 전언이면 전체 텍스트 수집 후에도 2차 전언일 수 있다.

참고 링크는 제공자의 확장 URL·게시글 HTML 앵커·본문 URL에서 찾는다. 자기 글 주소, 동일 URL, 알려진 추적 파라미터만 다른 주소는 중복 집계하지 않는다. 제공자의 확장 URL 목록이 있으면 본문의 `t.co`는 중복으로 제외한다. 아직 열어 보지 않은 서로 다른 단축 주소가 같은 페이지로 이동하는지는 사전에 알 수 없으므로 별개로 센다. 생략한 링크 주소와 원래 본문은 유지하고 `contentMeta.linkExpansion` 및 링크별 `skipped` 상태에 기록한다. 화면에는 링크 개수와 수집 생략 이유를 표시하며 접근 실패·미수집 건수와 구분한다. 새 DB 컬럼이나 환경변수는 없다.

기존 글은 저장된 `sourceBody`가 있는 **미분석 글**에 한해 다음 정상 준비 시 같은 규칙을 적용한다. 이전 확장 본문에 대한 읽기 캐시는 새로운 입력에 사용할 수 없어 해당 글의 캐시만 초기화한다. 이미 완료된 분석·확장 본문·캐시는 자동 변경하지 않고, 사용자가 명시적으로 원문 갱신한 경우에는 새 규칙을 적용한다. 원래 본문이 별도 저장되지 않은 과거 글은 임의로 잘라 내지 않는다. 과거 연결 수집이 실패해 이미 원글만 저장된 경우에는 기존 수집 설명·읽기 캐시를 그대로 보존해 같은 본문을 유료로 다시 요약하지 않는다. 기존 재시도 보류·전역 대기를 일괄 해제하거나 과거 글 전체를 재분석하지 않는다.

조사한 실제 사례 #83479는 원 게시글 10,253자에서 저장 본문 113,158자로 늘었다. 추가 구간은 Space Intel Report 기사 일부 약 770자, Peter B. de Selding X 게시글 약 330자, EU 「A vision for the European Space Economy」 약 98,700자, EUSPA 갈릴레오 발사 계약 발표 약 3,000자였다(제목·주소 포함 근삿값). 링크 11개 중 읽힌 내용을 붙였던 것이며 중요도에 따라 4개를 선별한 것이 아니다. 저장 응답으로 오프라인 검증한 새 규칙의 결과는 참고 링크 11개·추가 수집 0회·원 게시글 10,253자 유지다. 운영의 완료된 글 자체를 바꾼 검증은 아니다. 링크 3개 이하에 포함된 긴 문서에는 이 개수 제한만으로 길이 제한이 생기지는 않는다.

`원문 페이지 본문 추출`은 HTML 본문 추출에 성공했다는 뜻이다. 이미지/차트 OCR, PDF 읽기, 모든 동적 페이지 지원이나 유료 본문 전체 확보를 뜻하지 않는다. 접근 실패·인식 가능한 유료 미리보기·연결 원문 실패는 `일부 수집`으로 표시한다. 해당 소스에 이미 저장된 로그인 세션이 있을 때만 인증 본문 추출을 시도한다.

공개 HTTP 수집은 외부 주소를 검증하고 DNS 결과를 고정하며 이동 URL마다 다시 검사한다. 일반 페이지 제한은 요청당 15초, 이동 5회, 압축 해제 후 2MiB다. 제한에 걸리면 일부 수집으로 남기며 실패를 본문 절단 성공으로 취급하지 않는다.

## 전체 읽기와 비용

`analysis/fullReading.ts`는 원문 12,000자 이하를 구간 읽기 호출 없이 사용한다. 긴 글은 기존 캐시 호환용 12,000자 기본 구간을 유지하되, 미완료 구간은 첫 API 요청 전에 최대 6,000자씩 무손실 이등분한다. 모든 문자·끝 문단·이모지 쌍을 입력에 포함하고 원문 구간 전체의 사실 메모를 순서대로 묶는다. 후속 입력 예산 안에 들어오면 합계가 12,000자를 넘더라도 읽기를 완료한다. 예산을 넘는 경우의 제한된 정리는 아래 규칙을 따른다. 출력 메모는 원문 전문이 아니며 요약 과정에서 세부 정보가 줄어들 수 있다. 원래 수집 텍스트는 별도로 보존한다.

### 9/22 밤 확인한 재압축 반복과 수정 규칙

입력 상한 학습만으로는 해결되지 않는 별도 비용 경로를 운영에서 확인했다. 저장 본문 160,835자 사례는 캐시 111개·합계 611,360자를 남기고 `too_many_levels`, 64,410자 사례는 캐시 24개·합계 138,525자를 남기고 `not_compressed`로 보류됐다. 연결 원문을 포함하기 전 제공 본문은 각각 3,571자와 659자였다. 캐시는 부모·자식·압축 레벨이 중복되므로 이 수치를 원문 분량이나 API 횟수로 환산하지 않는다.

19:11~19:15:06의 명시적 단건 실행에서도 새 출력 제한 오류는 관측되지 않았지만 캐시가 78개에서 155개로 늘고 `too_many_levels`로 끝났다. 학습 입력 상한은 2,914자, 보정 횟수는 0이었다. 보정 횟수는 출력 제한 복구 호출만 세므로 전체 API 호출이 없었다는 뜻이 아니다. 이전 코드는 성공한 메모도 합계가 12,000자 이하가 될 때까지 최대 12개 레벨로 다시 요약했다. 모든 사건을 보존하라는 지시로 결과가 조금씩만 줄면 정상 응답에도 비용이 계속 발생했다.

이번 수정은 그 반복을 제거한다. 다음 구현은 전체 266개 테스트·타입 검사·프로덕션 빌드를 통과했고 운영 `e8ee7ce` 배포와 보류 글 3건의 분석 완료를 확인했다. 전체 글의 성공률·요약 품질 검증과는 구분한다.

- `packetBudget`은 글자 수(`maxChars`)와 UTF-8 바이트 수(`maxBytes`) 중 지정된 한도를 모두 검사한다. 기본 호출과 저장 다이제스트 재종합은 기존 12,000자 한도를 유지한다.
- 저장 피드의 준비 경로는 공식 `api.deepseek.com`과 설정된 API 키를 사용하며, 실제 선별·자료 정리·최종/선택적 심층 모델이 모두 허용된 Flash ID일 때만 **384KiB(393,216바이트)**의 사실 메모를 허용한다. 허용 ID는 `deepseek-flash`, `deepseek-v4-flash`, `deepseek-v4-flash-vision-exp`다. 실제 `LLM_EXTRA_BODY.model` 덮어쓰기도 검사하며, 다른 공급자·알 수 없는 모델·잘못된 설정은 12,000자로 돌아간다. 이 큰 예산에는 별도 글자 수 제한이 없다.
- 원문 `level=0`의 모든 구간 성공을 확인하고 그 순서로 조립한다. `readCachedSourceNotes`도 이 구간만 조회하며, 부모 체크포인트가 없어도 모든 자식 결과가 있으면 복원한다. 임의의 캐시 항목 전체를 합치거나 성공한 앞부분만 완성본으로 쓰지 않는다.
- 이미 완료된 전체 캐시도 현재 소비자의 예산에 맞는지 다시 검사한다. 더 작은 예산으로 바뀌면 기존 성공 구간을 보존하고, 과거에 이미 만들어 둔 완전한 압축 레벨 중 더 작은 결과도 추가 API 없이 재사용한다. 새 후속 압축 레벨을 반복 생성하지 않는다. 예산 축소 중에는 이전 완성 메모를 별도 필드에 보존하므로, 중단·재개해도 같은 입력과 성공한 압축 구간을 재사용하며 새 완료 때 임시 보존 필드를 지운다.
- 여전히 예산을 넘을 때만 별도 압축 지침으로 **새 정리를 한 차례** 수행한다. 한 차례는 여러 구간 호출일 수 있으며, 성공 결과를 저장해 중단 후 같은 정리를 이어간다. 모든 구간을 정리한 결과도 크면 `packet_too_large`, 응답이 잘리면 `output_limit`로 보류한다. 두 번째 새 정리 차수는 실행하지 않는다.
- 캐시 키·복구 `policy:2`·분석 지문을 바꾸거나 기존 보류를 자동 해제하지 않는다. 명시적으로 재개한 글만 저장 결과를 활용해 진행하며 원문·성공 메모·학습 입력 상한을 유지한다.

384KiB는 글 하나의 준비된 메모에 대한 제한이다. 시스템 지침·제목·여러 글의 맵 결과·최종 출력까지 합친 정확한 토큰 계수나 모든 모델의 문맥 한도 보장이 아니다. 이번 수정은 다이제스트 마지막 전체 입력의 전역 예산이나 큰 글의 맵 내부 분할을 재설계하지 않는다.

2026-09-22부터 내부 전체 읽기 지침과 사용자에게 보여줄 Feed 요약 지침을 분리한다. 내부 읽기는 서로 다른 사건·주체·수치·날짜·가격·제품·조건·반론·결론을 짧은 사실 항목으로 압축한다. 원문에 있는 영향·가설을 보존하되 새로운 투자 해석·연결 가설을 만들어 분량을 늘리지 않는다. 기존 사용자 요약 지침은 후속 선별에 그대로 적용한다. 선별은 늘어난 전체 입력에 맞춰 기본 출력 상한을 1,600토큰(논지 목록이 있으면 2,800)으로 조정하고 DeepSeek JSON 모드를 사용한다. 원문·판단 기준을 줄이지 않고 완성 JSON을 받을 여유를 확보하는 상한이며 고정 소비량은 아니다.

자료 정리 모델·Thinking 선택은 기존 Settings를 따른다(기본 OFF). 구간당 출력 상한은 OFF일 때 3,200토큰이다. 장문 첫 읽기에는 호출 비용이 추가되지만 이후 선별·다이제스트는 저장 결과를 재사용한다. 본문·수집 범위·모델·Thinking·사용자 요약 지침이 달라지면 캐시를 다시 만든다. 이번 내부 지침 수정은 기존 캐시 키 계산을 호환용으로 유지하므로 완료된 전체 읽기·기본 구간·하위 구간을 일괄 무효화하지 않는다. 사용자 요약 지침도 이 호환 키에는 계속 포함되지만 내부 API 프롬프트에는 주입하지 않는다. 모델 ID가 같은 별칭의 서버 측 버전 변경은 자동으로 감지하지 않는다.

구간마다 체크포인트를 저장한다. 출력 제한으로 실패하면 해당 구간을 추가 이등분하고 실패한 상위 구간의 계획을 하위 호출 전에 저장한다. 복구는 최대 3단계·추가 호출 24회이며 정상 사전 분할 호출은 이 보정 횟수에 포함하지 않는다. 해결되지 않으면 보류하고 잘린 응답을 완성 요약으로 저장하지 않는다. 새 복구 정책 v2는 이전 미완료 보류를 한 번 해제하되 완료 구간·기존 분할 계획을 보존한다. 같은 정책에서 재보류된 글은 자동으로 다시 풀지 않는다. 명시적 해제도 성공 구간을 재사용한다. 재시도·사용량 상세는 [LLM 사용량](LLM_USAGE.md)을 참고한다.

9/22 저녁 수정은 **한 글에서 배운 입력 상한을 이후 미완료 구간에 적용**한다. 예를 들어 6,000자 입력이 잘리면 무손실 반분 크기인 약 3,000자를 `recovery.inputCharLimit`에 먼저 저장하고, 같은 글의 뒤 구간도 유료 호출 전에 그 크기로 나눈다. 더 작은 구간이 실패하면 다시 낮추며, 앞 구간의 성공을 근거로 자동 상향하지 않는다. 보관된 실패 분할 계획은 완료 부모 안의 하위 계획까지 읽어 상한을 추론하므로 이미 실패한 큰 구간을 재호출할 필요가 없다. 이 사전 분할은 정상 처리이며 보정 횟수를 소모하지 않는다. 실패 직후 하위 보정에는 기존 최대 3단계·24회가 적용되고, 3,000자 미만 구간이 실패하면 해당 실행을 보류한다.

학습된 상한은 명시적 재시도에서도 완료 구간·분할 계획과 함께 유지한다. 기존 `policy:2`, 분석 설정 지문, 캐시 키는 바꾸지 않으며 이미 보류된 글을 일괄 해제하지 않는다. 같은 글의 여러 구간 실패가 누적될 수 있으므로 사용량 화면의 글별 실패 합계가 동일 구간 반복 요청을 뜻하지는 않는다. 더 작게 나누는 처리는 입력 전체를 보존하지만 실제 모델의 요약 품질이나 모든 글의 성공을 보장하지는 않는다.

피드 기반 다이제스트는 전체 읽기 실패를 숨기고 해당 글만 누락한 보고서를 저장하지 않는다. 기존 다이제스트들을 재종합하는 별도 경로도 모든 저장 텍스트를 읽지만 중간 요약은 영구 저장하지 않는다.

## 데이터와 배포

`0014_full_article_reading.sql`은 `articles`에 nullable 필드 3개를 추가한다.

| 필드 | 내용 |

Railway 시작 명령의 `db:migrate`가 적용한다. 기존 글은 필요할 때 준비하며 부팅 때 전체 재분석하지 않는다. 영구삭제는 새 본문/캐시도 지우고 중복 수집 방지용 묘비를 남긴다. 새 환경변수는 필요 없으며 기존 `FILTER_BODY_CHARS`, `DIGEST_ITEM_CHARS`, `MAX_BODY_CHARS`는 사용하지 않는다.

## 검증

9/13 도입 당시 `tests/fullArticle.test.ts`를 포함한 156개 테스트·타입 검사·프로덕션 빌드가 통과했다. 실제 공개 한국경제 기사 2건은 RSS 본문이 비어 있어도 원문 1,891자/3,700자를 추출했다. 로컬 데모에서 본문·수집 상태·저장 요약·갱신 버튼 표시를 확인했다. 운영 계정의 실제 LLM 보고서 생성은 이 검증에 포함하지 않았다.

9/22 입력 상한 학습까지의 `fullReadingRecovery.test.ts`·`fullArticle.test.ts`·`readingCacheRace.test.ts` 33개 가상 호출 테스트는 내부 프롬프트 분리, 첫 요청 최대 6,000자, 전체 문자/끝 사건 보존, 구 캐시 해시·완료 하위 구간 재사용, 정책 전환 시 한 번만 보류 해제, 보정 호출 상한, 수집 경쟁·삭제 후 쓰기 방어를 검증했다. 입력 상한 학습은 72,000자 가상 글의 실패를 12회에서 1회로 줄였고, 78,000자 글도 실패 13회 후 보류 대신 실패 1회 후 완성했다. 중단 후 기존 분할 계획에서 상한을 복구하고 같은 정책의 보류는 자동 해제하지 않는 것도 확인했다. 당시 전체 테스트 255개·타입 검사·프로덕션 빌드가 통과했지만 뒤의 운영 단건에서는 재압축 반복 보류가 확인됐다. 새 메모 예산·한 차례 정리 수정은 전체 **266개 테스트·타입 검사·프로덕션 빌드 통과**. 운영 `e8ee7ce`의 Railway 배포 성공·공개 health revision과 비인증 진단 조회 HTTP 401을 확인했다. 이전 재압축 보류 글 3건을 다시 분석했을 때 전체 읽기 추가 호출 없이 기존 메모를 재사용했고, 글마다 선별 성공 1회로 화면의 분석 완료까지 확인했다. 출력은 각각 955·619·773토큰이며 3건 합계의 화면 비혼잡 단가 참고 비용 증가는 약 $0.0092였다. 확인 사례에는 160,835자 `too_many_levels` 글과 64,410자 `not_compressed` 글이 포함된다. 이 결과는 해당 3건의 완료와 재사용 검증이며 모든 글의 성공률·사실 보존 품질을 확정하지 않는다.

운영 완료 확인은 위 3건까지다. 추가 한 건은 실행을 시작했지만 브라우저 연결 문제로 최종 결과가 미확인이다. 접근 복구 뒤 기존 실행 결과부터 조회하고 남은 읽기 보류는 필요한 글만 명시적으로 재개한다. 제공자 `content_policy` 보류 8건은 변경하지 않았다.

참고 링크 개수 정책은 전체 276개 테스트·타입 검사·프로덕션 빌드를 통과했다. 링크 3/4/11개 경계, HTML 인코딩·추적 주소 중복, 원문 보존, 외부 요청 0회, 기존 미분석 글 전환과 완료·동일 본문 캐시 보존을 검증했다. 유료 API 검증 호출은 하지 않았다.
